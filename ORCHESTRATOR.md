# ORCHESTRATOR.md — регламент Codex

## Назначение
Единый координатор разработки в Codex внутри Cursor. Скорость и качество MVP важнее экономии токенов. Не строить собственный оркестратор, App Server-интеграцию или обязательные TOML-профили до возникновения реальной необходимости.

## Стартовая маршрутизация
| Роль / задача | Модель | Reasoning |
|---|---|---|
| Оркестратор, интеграция | gpt-6.2-sol | high |
| Основная реализация | gpt-6.2-sol | medium; high при сложности |
| Критическое решение, анализ ТЗ, блокер, сложное ревью | gpt-6.2-astra | high; xhigh по необходимости |
| Адресный анализ файлов, типовые тесты и данные | gpt-6.1-terra | low / medium |
| Анализ донорского репозитория | gpt-6.2-sol | medium; Astra/high при сложности |
| Независимый поток | Cursor/Grok (назначает пользователь) | по возможностям Cursor |

Названия Sol и Astra приняты инструментом в диагностике, фактически применённая модель не была показана. Terra присутствовала в схеме, но не тестировалась. При недоступности модели использовать проверенную доступную альтернативу и сообщить об этом. Не применять max/ultra по умолчанию. Уровни — стартовые рекомендации, не оценка качества или стоимости.

## Цикл работы
1. Прочитать AGENTS.md, актуальные требования и относящиеся к задаче решения. Определить критерий готовности и критический путь.
2. Малые изменения выполнить самостоятельно; независимые содержательные задачи делегировать. Обычно не более двух одновременно работающих субагентов (третий — только если есть явный выигрыш времени и нет конфликтов).
3. Назначить непересекающиеся области записи до запуска. Read-only исследования можно проводить параллельно. Общие файлы и интеграцию оставить оркестратору. Grok по возможности работает в отдельном проверенном worktree; иначе выделяется отдельная область файлов и согласованный порядок интеграции.
4. Получать результаты через уведомления и статусы; не опрашивать агентов в плотном цикле. При зависании или блокере уточнить задачу, прервать либо эскалировать. После 1–2 содержательных неудачных попыток оценить причину и передать более сильной модели или изменить постановку. Критические задачи направлять Astra сразу.
5. Проверить diff, критерии приёмки и тесты, интегрировать изменения. Сохранить короткий статус и существенные решения. Не выполнять повторное полное ревью всего проекта после каждой мелкой задачи.

## Подтверждённый интерфейс текущей среды
По отчётам диагностической сессии доступны `collaboration.spawn_agent`, `list_agents`, `wait_agent`; запуск с разными `model`, `reasoning_effort`, `fork_turns: "none"` принят. Схема также содержит `send_message`, `followup_task`, `interrupt_agent`; применять согласно фактической схеме инструмента. Параметры `agent_type`, `cwd`, `worktree` и счётчики токенов по агентам в доступной схеме отсутствуют. Отдельное закрытие завершённого треда не подтверждено. Не предполагать наличие отсутствующих инструментов. При изменении среды проверить актуальную схему.

Пример логического набора аргументов запуска (не команда CLI):
```json
{"task_name":"task_01","model":"gpt-6.2-sol","reasoning_effort":"medium","fork_turns":"none","message":"<задание по шаблону ниже>"}
```

`fork_turns: none` по умолчанию для независимых задач; `all` только если история действительно необходима. Повторно использовать существующего агента для связанной задачи, если это снижает повторное чтение. Не запускать вложенных агентов без разрешения пользователя. Общий sandbox и workspace не обеспечивают разграничение записей между исполнителями.

## Шаблон задания (в message)
```text
TASK_ID:
Цель и бизнес-ценность:
Контекст: необходимые требования, решения, пути к файлам
Область чтения:
Разрешённая область записи: (или READ ONLY)
Запрещённые изменения:
Критерии приёмки:
Проверки:
Результат: краткий отчёт + изменённые файлы + проверки + ограничения
Не запускай субагентов. При блокере сообщи оркестратору.
```

## После получения полного ТЗ
- Astra: выделить обязательные требования, критерии оценивания, ограничения, условия сдачи и правила использования ранее созданного кода. Сформировать проверяемый список требований.
- Параллельно: Sol анализирует выданные mock-данные и варианты решения; Reference Analyst адресно исследует донор только по релевантным требованиям и при допустимости исследования. Не импортировать код на этом этапе.
- Сопоставить варианты, выбрать минимальный подход, покрывающий критерии оценки; затем фиксировать архитектуру и задачи. Если правила запрещают подготовительные работы или переиспользование, соблюдать их.
- Вести поисковую часть и бизнес-аналитику как равноправные обязательные направления согласно предварительным разъяснениям; сверить это с ТЗ. Заранее предусмотреть проверку пошаговой демонстрации, логов, расчёта стоимости запроса и материалов сдачи по официальному шаблону.
- Приоритет — ранний сквозной работающий сценарий и последующее улучшение качества, а не максимальная полнота отдельных компонентов до интеграции.

## Контроль лимитов
Пользователь проверяет общий Codex Usage Dashboard перед интенсивной работой и на контрольных точках. Не приписывать конкретный расход отдельным агентам без данных. Не путать лимиты разработки с себестоимостью runtime-запроса. При угрозе остановки критического пути уменьшить необязательные параллельные исследования, использовать Grok для независимых задач и предложить пользователю решение по тарифу/кредитам; не покупать автоматически.
